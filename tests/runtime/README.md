# Runtime host checks

During the automation storage refactor, the current configuration checks are:

- `bash tests/runtime/run_config_storage.sh`: production codecs, system migration, complete documents and references, real file replacement, configuration owner, variables, source views, rule publication/admission, top-level stop, source selection, manual backup/restore, startup migration, object API edits/deletion/mappings and verified configuration-pack application. The object and pack API cases use the production shared adapter and actual owner/file commit; signature verification is a controlled boundary in this suite.
- `bash tests/runtime/run_storage_paths.sh`: actual shared file mutations, storage API and Web upload handler against temporary real files. Configuration files, their temporary files and parent directories cannot be changed through these paths; reads, copies out and ordinary file operations remain available. The VFS path mapping and FAT alias lookup are controlled boundaries, not a physical-card test.
- `bash tests/runtime/run_rule_pack.sh`: the configuration checks above plus production signature/trust/recipient/decryption checks using the SDK MbedTLS library and disposable PKI.
- `bash tests/runtime/run_service_runs.sh`: production independent service records, fixed targets, reboot state, process-command builders and log observation.
- `python3 tests/runtime/test_service_control.py`: production service API, queue admission and executor entry connected to the durable run registry; configured ordinary background commands use the same route.
- `python3 tests/runtime/test_completion.py`: synchronous/asynchronous queue leases, timeout completion ownership and cancellation.
- `node --test tests/prompts/failure-catalog.test.cjs`: bilingual failure messages and their production callers.

The configuration suite uses temporary real files and actual SHA-256. Its NVS driver, SD driver, networking and PKI verification boundary are simulated. Partition initialization compiles the actual source in plain and encrypted modes; the system migration checks encrypted-file precedence and one-time widget migration. These driver mocks do not validate physical NVS encryption. The separate legacy-reader fixture runs the production upgrade reader against deployed record layouts; the separate crypto suite performs actual package verification. Rule/source/task/API function bodies extracted for the host build come from production sources, without copies of their algorithms. Native C checks use ASan/UBSan. Service checks simulate NVS, SSH transport and RTOS scheduling; they do not execute Linux process commands on a host. Retired protection/pin and duplicate-executor fixtures are replaced by these production paths, rather than maintained as alternate algorithms.

`bash tests/runtime/run_all.sh` is the broader integration entry point. It now uses the unified configuration wire format and current prompt regression checks; retired pending-restart and service-state deletion guards are no longer test authorities. Run the browser suites separately to exercise the complete production page scripts.

Requirements: a compatible C compiler, Python 3, Node, and ESP-IDF cJSON sources. `IDF_PATH` selects the SDK; the default is `/Users/massif/esp/v5.5.2/esp-idf`. On macOS, Apple Command Line Tools are used; the common hash boundary uses CommonCrypto, or OpenSSL on other hosts. Configuration executables are written under `/tmp/tianshan-config-storage-tests`; independent service executables use `/tmp/tianshan-service-runs-tests`.

Fixtures use synthetic hosts and credentials. These checks do not flash hardware, contact real SSH hosts, certify physical SD hot-plugging or power-loss behavior, or verify rendered browser layouts. Browser checks live under `tests/prompts`; certificate signing/parsing checks use `tests/certificate/run_host.sh`. Record host, build, browser and real-device evidence separately.
