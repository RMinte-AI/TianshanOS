## 1. 要解决的问题与实施原则

当前问题不是单一的容量不足：保存来源不统一、配置引用与服务占用混用、前后端删除判断不同、部分保存错误未向上传递，共同造成“保存不了、改不了、删不了、重启后行为变化”。

本次统一处理以下四件事：

1. 每种数据有唯一、明确的保存位置。
2. Rules、Action Templates、SSH Commands 的修改由同一个配置入口提交。
3. 删除本地配置与停止远端服务分别处理。
4. 新机制接管后删除旧机制，不保留两套同时工作的实现。

执行约束：

- 从用户需求和数据生命周期出发，不继续按已有补丁扩展分支。
- 不新增多级兜底、自动补数据、猜测成功、自动修复引用、通用重试框架或历史版本平台。
- 不新增兜底性测试、全组合状态矩阵或独立证据系统。
- 保留完成已确认行为必需的检查：管理权限、输入有效性、真实写入结果、引用处理、密钥保护。
- 写入失败不能报成功；保留原有完整副本是已确认的保存语义，不借此增加其他恢复功能。
- 仅增加职责明确的小模块，不建立可插拔存储框架、通用工作流引擎或多套兼容层。
- 只改本次涉及的代码，不批量格式化、不顺手重构无关功能。

### 2.1 必须保留的几个区别

- 系统设置修改后正常写系统配置区；自动化的手动副本按钮不控制网络、风扇设置。
- 自动化恢复不覆盖网络、风扇或密钥。
- 有卡时强删修改卡内当前配置，不偷偷更新内部旧副本。用户需要点击“保存应急副本”让删除结果进入副本。
- 使用旧副本可能看到其中的旧规则，界面必须说明当前来源和保存时间；这与正常 SD 模式下从旧路径误恢复数据不同。
- 无卡期间编辑的是内部当前配置；重新插卡时由用户决定保留哪一套。
- “最终强删”不绕过正常管理权限，也不能在存储无法写入时伪造永久删除成功。

## 4. 分区与系统配置方案

### 4.1 具体布局建议

保持现有已用分区的地址、大小；仅调整原 NVS 的标签并新增两项：

| 标签 | 类型 | 偏移 | 大小 | 职责 |
|---|---|---:|---:|---|
| `keys_nvs` | `data/nvs` | `0x9000` | `0xC000`（48 KiB） | 原 NVS 物理区域，改为密钥专用 |
| `nvs` | `data/nvs` | `0x9B0000` | `0x20000`（128 KiB） | 新系统配置区 |
| `auto_cfg` | `data/spiffs` | `0x9D0000` | `0x200000`（2048 KiB） | 自动化内部配置／副本 |

新增区结束于 `0xBD0000`；在当前 16 MiB 布局中仍有约 4.19 MiB 预留。`nvs_keys` 加密密钥分区、OTA 数据区、两个应用区、现有 storage、www 和 fatfs 不移动。

这里的标签调整有明确目的：ESP-IDF 的默认 `nvs_open()`，以及 Wi-Fi、PHY 等 SDK 自身的 NVS 使用，自动落到新的系统配置区；密钥代码显式打开 `keys_nvs`。这样不需要对几十处普通 NVS 调用逐个加路由，也不需要关闭 SDK 正常持久化功能。

原区域的字节不因改标签而擦除。迁移完成后，仅删除已迁移的非密钥记录。

### 4.2 系统配置归属

实施前从所有生产 `nvs_open`、`nvs_set_*` 和配置模块注册入口生成一次归属清单，直接补在本文件对应表中，不另建盘点平台。迁移归属与“哪份旧值有效”分别处理：普通模块原来可能 SD 优先、存在 pending_sync 时又是 NVS 优先，不能一律复制原 NVS 中的值。

| 数据 | 新位置／处理 |
|---|---|
| `ts_keystore` 中公私钥、索引、必要元数据 | 原位置 `keys_nvs`，密钥模块显式访问 |
| `ts_pki/privkey`、`ts_security/key_*` 等实际密钥 | `keys_nvs`；各模块将密钥访问与普通证书信息分开 |
| 证书、CA 链、SSH 已知主机指纹、用户认证配置 | 新系统 `nvs`，维持现有访问权限和安全语义 |
| 网络、Wi-Fi、DHCP、NAT、主机名 | 新系统 `nvs`，命名空间及值类型尽量保持 |
| 风扇、温度来源、USB 选择、设备监测、LED 基础设置、UI 偏好 | 新系统 `nvs` |
| OTA 服务地址、更新记录等非密钥系统数据 | 新系统 `nvs` |
| SDK Wi-Fi／PHY 数据 | 新系统 `nvs`，随默认分区标签迁移 |
| Rule、模板、命令、SSH 主机、数据源、需保存的用户变量定义 | 自动化配置集合，退出常态 NVS 保存 |
| 旧 `pending_sync`、旧镜像序号、旧规则存储 guard／bank | 仅迁移读取；不带入新的常态同步流程 |

混合命名空间按实际键的拥有者拆分，不把含私钥的整个命名空间直接搬进普通配置区，也不把含自动化定义的整个命名空间继续复制到系统区。

实施盘点（基于最新上游 `002d3a7b`）：

| 生产命名空间 | 归属 |
|---|---|
| `ts_keystore`；`ts_pki/privkey` | 留在原密钥物理区 |
| `ts_pki` 的证书、CA、状态；`ts_auth`；`ts_security` 的证书记录；`ts_ssh_hosts`（指纹） | 系统区；`privkey`、`key_*` 密钥记录留在密钥区 |
| `ts_net`、`ts_dhcp`、`ts_wifi`、`ts_dhcps`、`ts_nat` | 系统区；模块 `config` blob 与直接 NVS 字段分别保留旧读取语义 |
| `fan_config`、`ts_fan`、`ts_temp`、`usb_mux`、`ts_compute`、`ts_pins` | 系统区，HAL／驱动读取前迁移 |
| `led_boot`、`led_color`、`ts_led`、`ts_device`、`ts_system`、`ts_ui`、`ota_config`、`ts_ota`、通用 `ts_config` | 系统区 |
| SDK Wi-Fi／PHY 等 NVS 记录 | 系统区，保留 SDK 原始值类型 |
| `action_tpl`、`ts_auto_src`、`auto_rules`、`rule_stage`、`ts_ssh_cmd`、`ts_ssh_cfg`、`ts_rules`、`ts_actions`、`ts_sources`、`ts_var` | 留给自动化专属迁移，不复制到系统区 |
| `ts_meta/schema_v0…8` | 系统配置版本；旧 pending 等同步信息仅供迁移读取 |


### 4.3 初始化顺序

按依赖分三段，不让自动化迁移反过来阻塞基础系统：

1. 识别新布局，初始化 `keys_nvs` 与系统 `nvs`；先取得 SD 可用性，复制系统记录与公开证书，再按旧模块真实优先级导入系统文件。若旧文件加密，先离线加载证书与原密钥、初始化配置包能力，不启动网络注册。此时禁止普通模块先从空白新 NVS 生成默认值或启动自动保存。
2. 系统设置迁移完成后，启动网络、风扇及安全模块，独立挂载内部文件区。
3. 在密钥、证书和配置包能力就绪后，由自动化模块读取／转换旧自动化、准备完整运行视图、加载当前配置，再开放规则执行。

系统区必须在网络、风扇等模块读取配置前就绪；不能继续依赖固定延时 2 秒／3.5 秒来猜存储是否准备好。内部文件区复用现有 SPIFFS 能力，不新增文件系统依赖。

新区域只在明确的首次初始化路径格式化；已存在但无法读取的区域据实报错，不能自动格式化或自动重置。

自动化文件或旧配置包无法加载时，保留网络、登录和基础散热能力，使用户仍能查看原因、修正配置和操作强删；不以整个系统拒绝启动代替自动化错误处理。

`ts_config_partitions` 和系统迁移不能反向依赖 `ts_automation` 或启动规则执行器。系统迁移留在 `ts_config`；旧规则／模板／命令转换留在 `ts_automation`，由启动编排依次调用。不能因为复用迁移函数引入 `ts_core → ts_automation → ts_core` 的新依赖或初始化递归。

### 4.4 内部文件区必须独立挂载

不能直接再次调用现有单实例 `ts_storage_mount_spiffs()`：它只有一份 `s_partition`／`s_mount_point`，第二次挂载会让统计、卸载和格式化指向错误区域。

在存储组件新增固定用途的 `ts_storage_auto.c`，独立管理 `auto_cfg` 与 `/autocfg`；不更改原 `storage` 和 `www` 的挂载状态。创建、统计、卸载、格式化均显式指定 `auto_cfg`。保持 `format_if_mount_failed=false`；首次空白区域初始化与已有文件区读取失败分开处理。当前 SPIFFS 挂载数配置为 3，需核对原 storage、www 和 auto_cfg 恰好各占一项。

## 5. 一个自动化配置集合、一个提交入口

### 5.1 保存内容与路径

建议用固定的完整配置文件：

- SD 工作配置：`/sdcard/config/automation/state.json`。
- 内部配置：`/autocfg/state.json`，挂载 `auto_cfg`。

集合只包含明确业务字段：格式版本、配置版本、保存时间、用户启停自动化的设置、Rules、Action Templates、SSH Commands、必要 SSH 主机、数据源及需持久化的用户变量定义。复用现有字段含义；编解码本身必须只处理所给配置，不能查当前正在运行的管理器。

不把执行次数、活动队列、远端 ready/running、SSH 输出和实时变量值混入配置副本。用户显式配置的初始值按定义保存，不靠复制运行缓存凑齐依赖。

### 5.1.1 解码与引用解析分开

当前 `ts_rule_decode()` 遇到模板引用会调用 `ts_action_template_get()`。必须移除这个隐式实时查询：规则保存模板 ID 和该步自己的延迟／重复／条件；运行绑定从本次完整候选集合解析，不从旧集合补齐。同名模板在 SD 与内部内容不同，也必须使用正在加载的那份。

强删最后一个动作后，规则需要保留并停用，因此存储和 UI 必须接受 `enabled=false`、`actions=[]` 的待配置规则。只有启用／执行才要求至少一个有效动作及有效引用。不能复用当前“任何规则动作数组都不得为空”的校验，导致强删保存失败或重启无法加载。

### 5.2 代码职责

新增 `components/ts_automation/src/ts_automation_config.c` 及对应头文件，作为固定的业务配置入口，负责：

1. 当前工作来源、完整配置集合和版本。
2. 保存、加载、手动副本、恢复、插卡切换。
3. 普通编辑、引用替换及强删的整体提交。
4. 对已有管理器发布提交成功后的配置。

现有 rule/action/command/host/source 管理器继续提供业务读取与执行能力，但不再各自决定持久化来源、启动导入和镜像同步。不要在旧保存函数外再套一层同步后保留旧写入。

只使用一个配置修改入口与顺序，包含 CRUD、替换／强删、备份、恢复、来源切换和卡状态变化。保留现有规则版本校验；再使用这一入口唯一的 `active_version` 标识当前编辑上下文，所有写操作与预览执行均携带它。该值在来源切换、成功修改和重启后改变，避免两份配置恰好有相同 revision 时写错位置；不为每个对象新增一套版本机制。

“副本是否包含最新修改”比较配置内容指纹，排除来源和保存时间等元信息；不能仅比较独立递增的 revision 或不可靠的设备时钟。

### 5.3 提交顺序

`检查 active_version 与目标存储实例 → 产生本次结果 → 准备全部可失败的内存与运行视图 → 处理本次引用修改 → 保存到当前唯一工作位置 → 不分配内存地发布 → 返回成功`。

- 保存失败时当前生效配置不前进，界面保留用户草稿。
- 正常提交需要的规则数组、模板／命令索引、数据源参数等必须在落盘前准备好。落盘后发布只交换已经准备好的对象，不能再因内存不足出现“磁盘新版本、运行旧版本”。外部数据源是否连接成功不作为配置保存成功的前提。
- 复用现有文件替换能力，保留完成一次完整写入所需的临时文件和上一次完整内容；不新增长期多版本、循环修复或自动回灌。
- 借鉴现有 `ts_action_store.c` 的完整文件替换处理，合并到新的整套配置保存中；不继续每个模板一份独立恢复协议。
- SD 与内部采用同一种配置内容；不在 NVS 中再维护第二套 Rule JSON、模板和命令副本。
- 为格式化、保存临时空间和当前完整内容核算容量；字节不足就明确拒绝本次写入，不截断、不部分保存、不自动压缩换协议。
- `使用 SD 卡配置`只读取并启用，不改变内部副本；`保存当前配置到 SD 并使用`先完整写卡，再切换。
- 配置提交不进行 SSH 连接，不在配置写入期间等待远端停止。

### 5.4 文件提交点与组合操作结果

固定使用当前完整文件、一个待写文件和一次替换所需的上一份文件，不引入额外日志或长期多版本。写入、flush／fsync、完整读取校验后才能进入最终替换。SPIFFS 不允许直接 rename 覆盖已有同名文件，必须按明确的临时／旧文件顺序处理，不能假设它与宿主系统的文件替换相同。

最终完整文件取得目标名称是本次保存的提交点；之后清理上一份文件失败，不能把已成功保存的配置报告成“未保存、旧配置仍在”。启动只处理这一次尚未结束的文件替换，不扫描旧 NVS 或其他副本修补内容。若连最后替换是否完成都无法读取确认，则显示“无法确认保存结果”，不宣称成功或原配置一定保留，不自动重发写操作。

配置文件与系统 NVS 的来源选择不是一个原子写入。`将当前配置保存到 SD 并使用`按“写卡完成 → 保存来源选择 → 发布当前来源”执行；若写卡已完成但来源选择未保存，明确返回“已保存到 SD 卡，但尚未切换”，继续使用内部配置。重试只执行切换，不重做已确认写卡，不建立跨存储事务平台。

只有选择来源时才更新相关系统记录。所有运行视图和普通系统配置不跟随整套自动化编辑无条件重置；未修改规则的冷却时间、既有控制操作和未改数据源的连接保持，避免编辑名称也触发规则重新执行或重连全部来源。

## 6. 工作来源与插拔卡行为

| 场景 | 工作配置 | 本次编辑写入 | 用户可见行为 |
|---|---|---|---|
| 正常有卡启动 | SD | SD | 正在使用 SD 卡配置 |
| 有卡点击保存应急副本 | 保持 SD | 本操作写内部完整副本 | 内部副本保存时间更新 |
| 无卡／无法读取，内部可用 | 内部 | 内部 | 自动启用应急配置，按原规则条件工作 |
| 无卡且没有可用内部配置 | 无可加载配置 | 用户创建有效配置后写内部 | 基础系统正常；自动化显示尚未配置／无法加载 |
| 应急运行时插卡 | 先保持内部 | 继续写内部 | 显示两个切换选项，不自动覆盖 |
| 选择使用卡内配置 | 切到 SD | 后续写 SD | 当前内部修改保留，但不自动写卡 |
| 选择当前配置写卡并使用 | 写卡成功后切到 SD | SD | 卡内自动化被明确替换 |

实现要点：

- 来源切换集中在同一个入口；卡事件只报告挂载／卸载结果，不调用旧 `sync_pending`。
- 现有事件是“挂载／卸载完成”，不能当作物理插拔检测。板级配置目前没有接入卡检测引脚，`s_card != NULL` 也不能证明卡仍在。备份面板进入、用户刷新／检查 SD 卡以及来源操作调用同一显式刷新入口：无卡时通过现有 `storage.mount` 尝试一次挂载，有卡时读取实际驱动状态；成功挂载才发事件，随后显示已定的两个选项。定期状态读取仍读已知结果，不把每次 GET 变成重新挂载。实际 I/O 错误也报告卡状态变化。不新建常驻探测线程、重试定时器或要求客户新增接线；不承诺当前硬件不存在的即时插卡中断。
- 应急运行后尚未选择卡内配置时，保存必要的来源选择信息，避免一次重启绕过用户的选择。
- SD 运行中掉卡时，先阻止旧来源新准入，准备并加载内部现有配置，保存必要来源状态后发布；已开始的远端操作不撤回。不能把 SD 的当前内存内容偷偷写成内部副本。内部无可用配置时保持自动化不可运行，不继续拿旧 SD 内存冒充内部可编辑配置。
- 有卡但单次保存失败，先报告保存失败；不能把一次业务错误等同于用户选择切换来源。
- SD 中合法的空配置就是空配置，不自动从副本或旧 NVS 补回。配置内容损坏、卡无法读取、没有配置是不同结果。
- 切换、恢复后再重新判断条件；手动规则不能因此被当作自动规则执行。
- 同一后台服务不会因切换来源而直接重复启动，执行时仍按实际服务身份检查。
- 从进入编辑页到点击保存期间发生切换，旧请求以 active_version 不匹配明确拒绝并保留草稿，不把旧 SD 表单写入内部。一次保存绑定到开始时的挂载实例，拔卡换卡后不能继续向另一张卡完成旧请求；挂载／卸载不与配置提交交错。
- 正常启动没有待处理来源选择时使用可读 SD；曾进入应急模式、尚未作出插卡选择时，重启仍保留该选择状态。持久化的是用户使用哪份配置的选择，不是旧运行状态。

## 7. 引用、编辑与删除的统一合同

### 7.1 影响清单

统一收集目标的直接和间接引用，返回具体 ID、名称和将采取的操作。只处理选定命令及其实际依赖，不能因为 AGX 有服务而锁住无关 LPMU 配置。

需要检查 API／旧导入产生的直接命令动作，不能只遍历网页生成的 `template_id`。变量与数据源依赖按真实字段处理；变量暂未上报不应被误判为存储损坏。

普通修改共用配置时显示影响范围；纯名称、说明等修改不要求远端核验。新定义用于后续执行，正在执行的内容不因编辑被覆盖。

### 7.2 正常删除与替换

| 对象 | 无引用 | 有引用时的操作 |
|---|---|---|
| Rule | 硬删除 | 不因远端状态增加阻止条件 |
| 模板 | 删除 | 替换为另一模板，或删除模板、移除引用并停用相关规则 |
| 命令 | 删除 | 替换命令，或删除命令、处理关联模板、移除引用并停用相关规则 |

删除、替换、停用以及相关列表变化作为同一配置修改保存；不能保存一半后返回“成功”。普通删除不再先调用 SSH 核验。

替换引用时保留每个规则步骤自己的顺序、延迟、重复和条件；只替换所选 ID。删除和替换使用本次候选集合解码，不能让旧实时模板查询影响结果。启用规则的完整性在启用时检查，停用的待配置规则允许保存和重新编辑。

### 7.3 最终强删

前端有明确的最后出口，后端对应 `force` 操作语义，不把普通删除换个按钮名。

最终强删：

- 不受引用、unknown/running、远端离线、普通检查失败和配置来源的旧只读标记长期阻止。
- 清理目标定义及实际关联，停用受影响规则；Rule 本身强删则直接移除。
- 关联检查不可用时返回明确影响说明，用户可以确认“暂停自动化后强制删除”；第二次执行仍删除已确认的目标，不能重新卡在同一个业务预检。
- 所有删除仅修改当前工作配置；另一份手动副本不自动变动。
- 保留正常管理权限。存储不可写、真实写入失败必须报告，不能只从网页移除卡片冒充永久删除。

后端预览结果带现有配置版本，用户确认后的操作针对该版本；引用已经变化时重新展示影响，不用过期清单删除其他对象。这是实际删除范围的确认，不建立通用“审批凭证”系统。

最终强删直接处理统一配置集合中的目标，不能要求旧规则引擎先通过 loaded／recovery／引用遍历检查。运行时关联扫描不可用与整个配置文件无法读取是两种情况；后者据实报告读取问题，不能把无法解析的文件当作空配置重写。

“暂停自动化后强删”不能复用普通提交的“整套配置必须全部可执行”前提。只要完整文件语法可读、能定位目标，就执行目标删除和可确定的引用清理；保留其他原数据，并将自动化启停设置持久化为暂停，发布不准入任何规则的运行状态。剩余语义错误可在页面继续修正，不自动修补、不删除不相关数据。重启、恢复或插卡不能把这次明确暂停当作自动运行重新打开；只有用户修正并启用后才继续。若删除写入失败但暂停已经生效，分别说明实际结果。

### 7.4 执行中的对象

复用现有执行时取得固定配置内容的机制，改掉“有执行持有就禁止删除定义”的用法：

- 定义可以删除，不保留等待远端停止／等待重启的已删除 Rule。
- 尚未发起的相关执行取消，重复执行不再继续，删除后不能又从队列发起已删动作。
- 已经进入执行的处理正常释放其资源，不能通过强删提前释放仍被使用的内存。
- 已启动的远端服务不隐式停止。
- 必须保留真正防止重复 start／stop／verify 的控制；它们不再作为删除配置的前提。

定义修改与执行准入使用同一短临界区确定先后。排队、动作前延迟、重复间隔中的工作尚未进入执行，删除／切换后取消；已经取得执行资格的操作归入“已开始”，可以完成，不能承诺撤回已经开始的网络操作。保存成功发布新版本前完成准入切换；删除返回后，旧版本不能再取得新的执行资格。完成回调只释放原执行拥有的资源，不再按相同 ID 查找并修改后来创建的新对象。

## 8. 远端服务管理与状态

### 8.1 服务与配置定义分离

在 `ts_ssh_service.c` 保留服务管理职责。启动受管理后台服务前，就保存停止／核验所需的最小信息：独立运行身份、目标地址与端口、账户／密钥引用、计划使用的进程定位标识。不得复制私钥。启动后的进程信息归入同一运行记录。

这些信息不依赖模板／命令继续存在；必要的少量管理记录放系统区，保证重启后仍能找回核验和停止入口。它不是规则副本，也不保存“现在一定运行中”的结论。

为什么需要：否则“允许删除命令”与“删除后仍能停止服务”不能同时成立。这是已确认的服务管理功能，不是增加兜底层。

不能等删除时才申请槽位或首次写入管理记录，否则系统 NVS 满又会成为最终强删的新阻止条件。新服务无法保存必要控制记录时拒绝本次启动；已经启动的服务记录不因定义删除重新分配。旧服务记录在首次迁移时登记，随后定义强删不再依赖新建记录。

- 新服务记录使用独立 run_id，记录原定义 ID／版本，但不以定义 ID 或可修改名称作为运行记录主键。删除后重建同名同 ID 命令，旧服务与新服务不混用；更改主机也不能改掉旧服务的停止目标。
- 迁移时已运行的旧服务保留其原有进程定位方式到该服务记录中；服务结束后退出旧定位方式，新启动使用统一方式，不长期运行多路径猜测。
- 用户看到的服务管理入口保留在现有相关页面／状态区域，不另建重型服务管理系统。
- 服务控制记录删除与配置定义删除分开；确认服务结束后清理记录。
- 运行记录容量独立于命令列表槽位。删除 64 条定义但服务仍活着，不能释放／覆盖它们的记录以启动新服务。容量不足只影响新的服务启动，不阻止定义编辑、强删或已有服务停止。128 KiB 系统区预算须包括这部分记录。
- 服务完成、日志就绪等回执绑定 run_id 和原定义版本。定义删除或来源切换后，旧回执只能更新独立服务项，不能重新创建已删变量、写入同名新命令的状态或触发新来源规则。
- 运行记录保存定义引用时遵循各对象原有 ID 长度，不复用旧服务结构中 32 字节的规则字段截断 64 字节规则 ID；否则不同长 ID 可能串记录。
- 普通后台指令已有的停止入口也要盘点接入，不能只处理 service_mode 而遗漏现有 nohup 控制。同步一次性命令不新增运行历史库。

### 8.2 状态含义

| 后端事实 | 产品显示 |
|---|---|
| 本次核验确认进程存在 | 服务运行中 |
| 本次核验确认进程已停止 | 服务已停止 |
| 控制操作正在执行 | 正在启动／正在停止／正在检查 |
| 网络、认证或进程检查失败 | 无法确认，并说明原因 |
| 只有缓存结果 | 标明上次检查结果与时间，不能当作本次确认 |

普通缓存读取与实际远端核验继续分工清楚。用户点击核验、启动、停止时获得实际结果；页面进入／手动刷新需要核验时复用现有控制入口，不新增高频 SSH 轮询或无上限重试。

不因为业务当前空闲就说服务停止；不因为终态回执还在就说操作仍在进行。重启后保存的管理记录初始是待检查，不把旧 running/ready 当作现在的事实。

## 9. API 与前端改动

### 9.1 API

保留现有各对象列表／读取／编辑入口，内部统一委托新配置入口，避免要求用户重新学习三个功能。

新增功能集中在少量明确接口，建议命名：

| 功能 | 建议入口 | 说明 |
|---|---|---|
| 来源、卡状态、内部配置时间、差异状态 | `automation.config.status` | 小响应，不在刷新时传整套 JSON |
| 保存副本 | `automation.config.backup` | 当前 SD 配置完整写内部 |
| 恢复／来源切换预览 | `automation.config.preview` | 返回当前版本、差异对象和覆盖范围 |
| 恢复／切换执行 | `automation.config.apply` | 固定的恢复或切换操作，不做通用流程引擎 |
| 删除影响预览 | 现有删除入口的 `preview` 参数 | 同一后端规则，不另写前端依赖算法 |
| 替换／最终强删 | 现有对象操作扩展 | 明确的 `replacement_id`／`force` 等参数 |

接口名称可按现有注册约定调整，业务语义不得分叉。新增接口需要核对 API 注册数量，避免超过当前 288 的配置上限后部分功能未注册。

写操作返回实际完成结果，以及删除对象、停用规则、当前来源和 active_version 等界面需要的数据；所有修改入口包含同一个编辑上下文检查。业务受限、资源缺失、写入失败、远端连接失败分别表达，不以一个 `service_busy` 覆盖全部原因。组合操作和无法确认提交的结果按第 5.4 节返回，不能笼统承诺旧数据未改变。

内部存储字段不直接替换现有 API JSON。保留当前接口中 serviceMode、varName 等已使用字段和单位的对外含义，集中在现有编解码／API 适配层转换，避免重写存储后前端读不到后台服务属性。

### 9.2 UI 操作清单

1. 自动化页顶部增加“配置与备份”入口，沿用现有菜单／sheet。
2. 面板显示当前来源、SD 可用性、内部保存时间、是否有未进入副本的修改。
3. 有卡提供“保存应急副本”“从应急副本恢复”。
4. 应急运行插卡后，提供“使用 SD 卡配置”“将当前配置保存到 SD 卡并使用”，另有取消／暂不切换。
5. 三个列表均有正常删除和最终强删出口；有引用显示名称、替换和删除关联选项。
6. 删除成功显示实际结果，例如“命令已删除，2 个模板已删除，3 条规则已停用”。
7. 删除不再因浏览器发起的远端核验失败而中断；“先停止服务再删除”只作为用户明确选择的服务操作。
8. 来源变化后刷新相关列表；保留尚未保存的用户输入，不让迟到响应把新页面或新来源覆盖。
9. 无卡资源缺失时显示“找不到图片，请插入 SD 卡”等具体原因；沿用规则本身已有的失败处理，不新增一套自动跳过全部错误的策略。

## 10. 迁移与 USB／串口包

### 10.1 一次性迁移

迁移是固定版本的入口，不是常态运行的多来源兜底。

1. 识别新布局，原 NVS 数据仍位于 `keys_nvs`。
2. 暂停普通模块初始化写默认值／自动保存，先按旧模块真实优先级解析系统值：有 pending_sync 时读取旧 NVS，否则读取有效旧 SD 来源；原来直接 NVS 的模块按原方式读取。将解析结果写入新系统 `nvs`，保持类型、认证版本和记录完整性，核对后才允许网络／认证等模块正常初始化。不能先运行 `ts_auth_init()` 再迁移，否则空白新 NVS 会触发默认账号重建。
3. 对旧自动化按持久化的最新已提交集合和各管理器实际权威来源读取，包含已经保存、等待重启才生效的新增／更新／删除。不能以旧运行快照或可见目录覆盖最新已提交结果；必要的配置包接受记录和签名校验保留。
4. 用上述确定的完整已提交配置建立新集合，保留 ID、规则步骤参数和引用；不将 SD 与 NVS 的不同版本盲目合并。新规则编解码为纯函数，不能为转换启动旧模板管理器去查询实时对象。
5. 有卡时将新工作集合保存到 SD。内部首次副本仅由用户手动保存，不能把迁移当作未授权的自动备份。
6. 无卡且旧 NVS 中存在自动化时，迁移为内部当前配置，进入已确认的应急模式；这不是“有卡时自动更新副本”。
7. 写入、读取核对和发布完成后，记录迁移完成，并清理原密钥区已迁非密钥数据。
8. 完成后只加载新格式；不再从旧 NVS、旧 JSON 目录、旧 `.tscfg` 或旧 bank 自动恢复配置。

系统与自动化的迁移完成分别记录，完成标记先于旧记录清理。已经发布完整新集合但清理失败时，下次只清理旧记录，不能再次导入让旧规则复活；标记尚未完成但新集合已经存在时，按新格式中的迁移版本确认已完成部分，不盲目覆盖。尚未完成的部分保留原数据和明确失败原因。进度仅用于这次版本迁移，不形成常态双读或重试平台。

旧系统值解析集中在系统迁移源文件，旧自动化转换集中在自动化组件内的迁移文件，目的仅是让已售设备升级；完成支持周期后可独立移除，不参与每次 CRUD。

导入／导出配置包仍保留现有签名与权限要求。配置包作为导入来源，不再成为隐藏的第二生效位置。最终强删不修改原签名包、不伪造验签；本地安装内容发生修改时，不能继续宣称它与原包内容完全一致。旧来源只读标记不能阻止用户已授权的最终删除。

### 10.2 升级包

- 包含匹配的应用、网页资源、新分区表和必要引导文件；写入地址从构建产物生成，不另维护一套手抄偏移。
- 提供可直接使用的 esptool 刷写脚本及客户说明，不要求客户安装整套开发环境。
- 默认不执行 `erase_flash`，不写空白密钥镜像，不格式化 SD。
- 新系统区／内部文件区只在首次初始化创建；重复刷包不清空已有设置或应急配置。
- 包内记录固件、网页、布局版本及文件校验值，沿用现有 manifest 工具，不另建发布系统。
- 本方案调整默认 NVS 标签，旧固件不应继续在新布局上运行：首次升级新布局的串口包将两个 OTA 应用槽位写入同一匹配版本，并设置正确引导信息，避免失败启动时进入不兼容旧应用。之后的正常更新按现有 OTA 流程处理，不重复清空数据分区。
- 更新 Root/Admin 密码恢复固件与说明，确保它访问新系统认证区，不误改密钥区或返回不兼容旧槽位。
- 普通新版本固件更新不重写系统配置区和内部自动化区。旧布局升级到新布局通过本次串口包完成，不把普通 app OTA 宣传成会更新分区表。

## 12. 实施顺序与每阶段出口

不以“先增加一个按钮、再到处修失败”为顺序。先完成数据与生命周期，再接 UI。

进入实施时先按当时仓库状态准备隔离分支／工作区，保留现有未提交工作；不直接覆盖脏 main，不 reset、不自动 stash，也不拿本文的旧 HEAD 覆盖后续修复。需要带入的现有修复按文件和实际 diff 确认。

| 阶段 | 具体工作 | 阶段出口 |
|---|---|---|
| P0：基线与归属 | 核对分支／脏改动；列 NVS 使用者、入口和旧来源优先级；量化 64 条完整配置、运行记录和系统区用量，以及旧视图＋候选视图＋解析／序列化的峰值内存 | 数据归属、布局、真实空间与内存、修改文件清单确定；不以 64 条计数代替体积预算 |
| P1：新分区与迁移骨架 | 新表、显式密钥区、新默认系统 NVS、系统数据迁移、初始化顺序 | 网络／风扇等能从新系统区工作，密钥未改变，旧自动化可被迁移读取 |
| P2：统一自动化保存 | 纯编解码、新集合、独立文件挂载、提交点、先准备后发布和 active_version；管理器接入 | 有卡只写 SD，无卡写内部，提交结果真实且无半套发布；旧写入逐项退出 |
| P3：来源切换与完整副本 | 手动备份、恢复、应急自动启用、插卡两个选项、64 条贯通 | 产品模式表可通过 API／CLI 验证，基本系统配置不随恢复改变 |
| P4：执行／服务与删除 | 启动前保存独立运行记录、准入与取消、停用空动作规则、普通替换、最终强删、持久化暂停 | 离线／unknown／正在运行时均可强删；不因删除时新增 NVS 写入受阻，重启不误恢复运行 |
| P5：UI 与文案 | 配置面板、删除影响与结果、来源提示、真实状态、中英文及规范适配 | 新路径在实际生产页面可操作，前后端一致，不依赖旧核验阻断 |
| P6：移除旧机制 | 删除旧保存／同步／保护路径及旧测试断言，更新说明 | 每种配置只有新入口；不依靠死代码或旧模块维持通过 |
| P7：构建与串口包 | 完整固件／网页构建、布局和包检查、同布局实机升级及定向验收 | 可交付客户包；源码、构建、主机测试和实机结果分别说明 |

每个阶段完成所属旧代码清理，不把所有清理拖到最后。后续仅在新变更或实际失败需要时重跑相关检查，不制造重复全套测试循环。

## 13. 必须删除／收敛的旧代码

| 旧内容 | 处理方式 | 允许保留的部分 |
|---|---|---|

## 14. 最小必要验证

验证针对用户已确认的结果，不新增通用故障注入平台、全排列矩阵、长驻监控、自动重试测试或与实现同义的空断言。

优先改造已有 `tests/runtime`、`tests/prompts` 和 `tests/macos27` 中对应检查；新测试只补真实合同缺口。主机测试使用实际生产编解码／保存／删除函数，不能只在替身中重写一遍新算法后宣称固件正确。

|---|---|---|
| V01 | 旧分区迁移并再次启动 | 原密钥不变；SD 优先／pending_sync 的有效设置保留，账号不重置；待重启规则变更不丢；完成后只清理、不重复导入 |

| V06 | 实际文件替换及发布前失败 | SPIFFS 与 SD 均走真实保存函数；内存准备失败发生在落盘前；提交前失败／提交后清理失败结果不同，不增加故障排列平台 |

| V08 | 关联检查无法完成时最终强删并重启 | 先显示暂停影响，确认后删除；不重新落回全量可执行检查；暂停保留，用户修正后才能启用 |
| V09 | 排队／运行中删除再创建同名命令 | 准入先后明确；旧回执不污染新对象；运行记录已在启动时保存，容量不足不阻止强删；原服务仍可停止 |
| V10 | 远端运行、已停、连接失败、仅有缓存 | 状态与原因真实，不因其他主机服务而锁定；无错误的运行声明 |
| V11 | 无卡时依赖图片／字体的动作 | 具体资源提示；不假报成功；不借机改变其他动作的失败策略 |
| V12 | 中英文、窄屏、长名称及确认取消 | 实际生产 UI 可完成操作，无重复弹窗、错误对象或迟到响应覆盖 |
| V13 | 最终压缩网页与完整固件构建 | auto_cfg 不覆盖 storage／www 挂载状态；旧 API 字段兼容，API 均注册，www 未超容量，未遗留旧写入口 |
| V14 | 同布局 ESP32 USB／串口升级与重刷 | 密钥保留、配置迁移、两个应用槽位兼容；重刷不清空内部配置 |

现行核心入口：`tests/runtime/run_config_storage.sh`、`tests/runtime/run_rule_pack.sh`、`tests/runtime/run_service_watch.sh`、`test_service_control.py`、`tests/prompts/delete-protection*`、`delete-reference*`、`service-ownership*`、`rule-pack*` 以及现有设计系统布局检查。先确认各入口与新合同的关系，不能原封不动保留旧的“拒绝删除即正确”断言。

## 15. 收敛与完成标准

实现阶段只维护四个明确的责任归属：

| 责任 | 唯一归属 |
|---|---|
| 密钥／系统基础设置 | 分区初始化及现有系统配置模块 |
| 自动化配置、工作位置、引用修改与持久化 | 新统一自动化配置入口 |
| 已发起执行、远端服务身份与控制 | 规则执行器／服务管理器 |
| 展示、用户选择、中英文表达 | WebUI，业务结论来自后端 |

最终审查逐项回答：

1. 是否还有常态自动化定义写回 NVS，或两个启动入口争夺权威？
2. 是否还有删除配置必须先证明远端已停止的路径，包括 API、CLI 和配置包入口？
3. 强删是否真正写入当前工作配置，是否阻止后续使用已删定义发起执行？

### 18.2 实机发现及根因修正

1. **主任务栈不足**：旧 4608 字节预算在真实迁移启动中溢出。先移除只用于比对身份的完整命令栈复制，并复用一份临时命令内存；完整迁移诊断峰值为 5264 字节。产品 main 设为 8192；普通构建实测使用约 3.9 KiB、剩余约 4.2 KiB。16 KiB 仅为诊断构建，不进入客户候选。
2. **旧数据与新导入策略混用**：旧非 Rule 管理器原来使用签名及接收者校验，却被套上新包导入的显式签名根要求。迁移恢复原加载语义；受保护 Rule 和新导入仍使用严格策略，不关闭验签、不在失败时转明文。修正后原 3／5／2／2／1 集合迁移成功。
3. **未加载提示失真**：列表保留底层失败原因；配置未加载时不再声称正在使用 SD。实际 owner 与中英文浏览器检查覆盖此行为。
4. **旧系统文件重新覆盖**：系统设置迁入新 NVS 后，个别所属模块仍读卡或回写。清理温度、电压保护、LED 和主机指纹的旧路径，明确首次转换与正常读取的边界。
5. **电压保护假保存**：旧通用 NVS 后端跳过超过 15 字符的键却返回成功，电压保护的长键因此没有实际保存。所属模块改为在 `ts_power/policy` 完整保存配置，API 统一读取实际运行配置，部分参数修改保留其他当前值。实机已恢复原 300 秒关机延时及其余原参数，保存、省略字段请求以及真实重启后的完整参数对比均通过。
