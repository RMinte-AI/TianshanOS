## 发现及决策

### R1 / P1：卡片显示与启动方式混用；保留条件还必须补后端判断

**已确认。** `components/ts_webui/web/js/app.js:4341` 使用 `r.enabled && r.manual_trigger` 筛选卡片。切换自动模式时字段变 false，卡片被过滤，日志和停止入口一起消失。

`app.js:22027` 附近提交逻辑只在非手动模式收集条件；手动保存把条件数组写成空。附件关于“条件会丢失”的判断正确。

**附件遗漏：**`components/ts_automation/src/ts_rule_engine.c:686` 的 `ts_rule_evaluate()` 只检查 enabled、冷却时间与条件，不检查 manual_trigger；`:657` 通过空条件返回 false 间接避免手动规则自动执行。仅在 UI 中保留条件，会使手动规则重新参与自动判断。

修复应把卡片可见性与启动方式分开，后端明确跳过仅手动规则，再允许保留自动条件。已有手动卡片、服务型模型规则可作为旧配置的默认显示集合；缺省与明确 false 必须区分，避免用户隐藏后又被重新显示。字段须贯通列表/详情 API、NVS、SD JSON 和配置包导入导出。已被旧版本清空的条件无法凭空恢复，必须提示补配。

### R2 / P1：保存规则可能丢配置、重置运行历史，还可能假报成功

**日志与源码确认删除/重建；异常损失属于代码风险，日志未发生。** `app.js:22106` 附近先调用 delete，再 add，且没有检查 delete 的业务 code。网络中断或新规则校验/分配失败发生在两步之间，会留下已删除状态。新建规则在 `ts_rule_engine.c:430` 附近 memset，重置触发时间/次数；冷却状态变化可能改变再次触发行为。

后端 `ts_rule_register():353` 已有同 ID 原位更新分支，**但不能直接认为它安全**：先释放旧数组，再分配新数组；分配失败仍可返回成功。新增分支也没有完整处理分配失败。`ts_rules_save():2323` 先清空旧 NVS，单条序列化/写入失败可能只打印警告；上层注册/删除不传播保存错误。SD 文件以 `fopen("w")` 直接覆盖，导出结果也没有完整传回。因此“保存成功”不保证重启后能恢复。

修复：准备并验证完整新配置后再替换，避免先删；保留适合保留的运行统计，定义修改条件/动作时何时重新评估；持久化错误返回给用户。不能宣称 NVS 与 SD 多次写入是一个原子事务。对旧配置包优先级也要保留：启动加载优先 SD，且同名 `.tscfg` 优先于 `.json`，不能只更新 JSON 后声称一定生效。

### R3 / P1：运行中编辑规则存在释放后使用风险

**源码确认危险交错，未在该实机日志观察到崩溃。** `ts_rule_engine.c:686` 的 evaluate 在取得规则指针后解锁，再读取条件和动作、执行网络操作；手动 trigger（`:808` 附近）也把内部动作指针带到锁外。与此同时 unregister（`:481`）可释放数组并移动规则，register 可释放并替换数组。`ts_rule_get():568` 同样返回解锁后的内部指针。

可能结果是偶发崩溃、执行错误动作或把统计写到另一条规则；“改为原位更新”本身不能消除这个问题。

修复：在短锁内取得本次执行所需的有界快照或明确的对象使用权，锁外执行网络操作，结束时按稳定 ID/版本回写。不要持全局规则锁等 SSH。对 ESP32 要限制快照尺寸和并发执行数量，而不是复制整个规则库。

### R4 / P1：状态未知被当成未运行；ready 也不是持续健康状态

**源码确认；本日志没有模型后续退出的证据。** `app.js:4370–4446` 的进程检查在熔断、SSH 错误等情况下把 isRunning 置为 false，再显示“未运行”并允许触发。API 业务失败也未先验证 code。可能只是暂时查不到，却误导用户再次启动。

`ts_ssh_log_watch.c:263–268` 一旦找到就绪字符串就写 ready 并退出；UI 后续 3 秒轮询（`app.js:4490` 附近）主要读取该变量，不是持续远程健康探测。卡片的进程检查也不是每 3 秒重新执行。因此页面可能保留历史 ready。自动规则链依赖该变量时也有相同语义问题。

另外 `ts_action_manager.c:1434` 启动日志监控失败只写警告，没有同步变成可靠的失败状态；命令发出成功不能代表模型启动成功。

修复：至少分清“启动中、已就绪、已停止、检查失败/状态未知”，带观测时间；未知时不能据此放行重复启动。后端也要提供重复启动保护，不能只靠按钮禁用。就绪后的低频健康检查应按主机合并、有界执行，避免每张卡片各自高频 SSH。

### R5 / P2：每次查日志都重新认证，ESP32 做了大量重复工作

**日志与源码吻合。** 文本中有 120 条 SSH 连接/认证完成记录、100 条 Checking log、101 条结果记录；绝大多数日志属于 SSH 与密码学细节。`ts_ssh_log_watch.c:98–219` 每轮加载私钥、建会话、连接认证、执行 grep、断开并释放。

配置是完成一次检查后等 3000 ms，实际正常连续轮次大约相隔 4.75 秒。120 对 signv 开始/结束日志的耗时中位数约 722 ms，范围 711–1175 ms。**这是日志测出的墙钟时间，不能换算成 CPU 使用率。**检查本身大约 1.7 秒，也包含网络/调度等耗时。

修复优先级：先减少握手次数与 INFO 调试日志；复用受限数量的主机连接或一次远程等待/合并检查，并设置真正的截止时间与取消。避免为每个模型建立永久独立连接。监控任务当前每个申请 8 KiB 栈，多模型扩展前须测内部堆、栈余量、并发上限。

### R6 / P1：自动化 SSH 没有和网页操作保持相同的远端身份检查

**源码确认，不代表此次发生攻击。** `ts_api_ssh.c:321–335` 在 connect 后验证 known_hosts；但 `ts_action_manager.c:1329–1345` 和 `ts_ssh_log_watch.c:185–195` 连接后直接执行命令，没有对应验证。SSH 客户端 `ts_ssh_client.c:293–316` 本身也没有提供主机信任检查。

日志中网页路径有 Host key verified，而自动模型启动/日志轮询路径没有；这与代码一致，不能把网页曾验证过等同于后续连接都已验证。

网页验证位置也晚于用户认证，因为 connect 实际包含认证。密码模式下，不能等凭据已经发出后再拒绝错误主机。

修复：将连接分为握手、主机信任校验、用户认证；所有自动/手动路径统一遵守。自动任务遇到未知或变更指纹应停止并报告，沿用现有人工信任流程，不自动接受新指纹。

### R7 / P2：日志本身存在截断与并发串行化问题，且打印密钥文本前缀

**日志确认格式损坏；具体每条损坏来源不能仅凭记录唯一归因。** 207、210、241、2997 行等长命令被截断/拼接；211、246 等处有重复行。

`ts_log.c:1000–1038` 用共享 static 512 字节缓冲和共享 in_hook；格式化无互斥，输出前已清除 in_hook。并发线程可覆盖尚未输出的内容；长行会截断。当前 SDK log v1 直接调用 hook，没有替这个缓冲加锁（已核查本机 SDK 源码）。当前配置启用该 hook，环形日志仅 500 条，密集调试内容也会挤掉历史线索。

`ts_ssh_client.c:424` INFO 打印私钥文本前 50 字符，日志有 120 条；并非完整私钥，也不能据此断定私钥已可被还原，但不应保留这种输出。去掉密钥文本、降低密码学内部调试级别；日志改为有界且线程安全的格式化/输出，明确截断，不长时间持有临界区。

时间戳在不同 tag 之间偶有约 1 秒回退；自建 TS_LOG 使用 esp_timer、ESP_LOG 使用 SDK 时间源，不能将这种差值直接认定为设备时钟故障。

### R8 / P1：日志监控替换/取消的生命周期不安全

**源码风险，当前日志没有重复监控替换或强删任务证据。** `ts_ssh_log_watch.c:293–313` 任务退出会自行 free(task)；`:331–345` 替换同名任务时，调用方解锁后轮询 existing->is_running，旧任务可能已释放它。stop/stop_all（`:407`、`:468`）有类似问题，还会强制删除可能正在 SSH 操作中的任务，绕过 socket、会话和私钥缓冲清理。后两 API 未检出外部 C 调用者，不能说当前常规操作必经强删。

修复：明确谁持有对象、谁负责释放，以完成通知确认退出；网络调用可取消、等待有界，避免依赖已释放对象的标志。重复启动新监控前确认旧监控已退出或用代次隔离，防止旧任务覆盖新状态。

### R9 / P2：配置了超时，不代表 SSH 各阶段都能按时退出

**源码风险，日志里没有连接卡死。** `ts_ssh_client.c:293` 的握手 EAGAIN 循环、`:316` 的密码认证循环反复 wait_socket，没有总截止时间；已有 SO_RCVTIMEO/SO_SNDTIMEO 不能替代整个重试循环的截止时间。日志监控自己的 600/800 秒超时只在每轮调用前检查，若卡在连接里，外层无法及时终止。

修复：连接/握手/认证/执行共享单调时钟截止时间，等待时检查取消；不要仅增加外围定时器或到期强删任务。

### R10 / P2：日志匹配字符串并未真正转义

**静态确认，本次字符串不含危险字符，未触发。** `ts_ssh_log_watch.c:130–158` 虽称转义，实际只是 strncpy，然后把 pattern 与路径放进 shell 单引号。包含单引号时可破坏命令，导致检测错误甚至改变执行含义；snprintf 截断也未完整检查。

修复：统一 shell 参数编码并校验长度，固定字符串 grep 使用明确选项边界。不是要求禁止用户使用正常的包含引号的日志文本。

## 对附件“最佳方案”的结论

方向正确，但不足以直接作为完整实施纲要。批准实施前应补齐：

1. 可见性独立；规则禁用不应让仍运行模型的管理入口一起消失，需明确产品语义。
2. 保留条件的同时，后端真正执行仅手动语义；旧版丢失条件要提示恢复。
3. 以安全更新代替删除重建；先解决分配失败、持久化错误和运行中对象生命周期，不能只换 API 调用。
4. “不重复启动”由后端保证；未知状态不能当成停止；定义用户主动停止后是否允许自动规则再拉起。当前字段不足以表达维护暂停，此项需要产品决策，不能私自选择。
5. 不把模型 ready 文本匹配当作长期健康；后续探测要有频率/并发预算。

推荐分包：第一包修模型卡片、模式切换、规则安全更新与状态真假；第二包统一 SSH 信任、生命周期、超时并降低轮询成本；日志可观测性修复可与第二包同步。都不需要重做全局 OS 架构。

## 建议实机补测

- 按自动→手动→保存→自动操作：卡片存在、条件不丢、手动期间条件为真也不自动启动。
- 模型正在启动/运行时修改规则：不崩溃、不串规则、不重复拉起；保存故障后旧规则可用且界面报错。
- SSH 暂时断开：界面显示未知而非停止；恢复后状态收敛；连接黑洞能按截止时间退出。
- 模型 ready 后杀进程：状态及时失效；用户主动停止后的自动恢复策略符合产品选择。
- 替换 SSH 主机指纹：所有自动与手动路径均拒绝，不能先执行命令再验证。
- 多模型连续启动/取消：监控任务、连接、内部堆和栈余量无持续恶化；日志无密钥文本及串行损坏。
- 使用新证书固件另跑证书报告中的硬件验收，记录镜像 SHA，避免只用 0.5.1 版本号区分镜像。
