# macOS 27 实机视觉审查：未达到验收标准

日期：2026-09-29。当前任务按用户最新指令先检查、列出问题，不修改生产实现。

结论：当前实现仍是旧组件布局、旧状态配色与新增玻璃外壳的混合。背景、部分卡片和公共字体已调整，但按钮角色、设置行、弹窗结构、材质分层和字号体系没有一致落实。不能认定为 macOS 27 风格完成；此前的功能/溢出检查不能支撑视觉验收通过。

## 二、每一层材质差在哪

Apple 将 Liquid Glass 用于控制/导航层，内容层采用适合阅读的标准材质；透明度取决于用途、背景与系统设置，并非每块都越透明越好。[Apple Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

| 层级 | 当前实现 | 实机对照与缺口 |
|---|---|---|
| 页面背景 | 已批准暖金/浅蓝渐变 | 方向保留，不能把背景调整当成组件完成 |
| 主内容 | 约 93% 白色承载面 | 接近白色符合稳定阅读方向；内部仍需清晰分组和间距 |
| 一级分组 | 浅灰/白色混合 | 原生浅灰设置组边界安静、行对齐；当前不同模块的框、标题、留白不统一 |
| 内部分组 | 约 15%、25%、50% 白色及实体白/灰并存 | 材质没有按角色命名和使用。编辑区较实可以正确，但普通嵌套板不应重复加框 |
| 顶部导航 | 白色约 44%→19%，blur 22、saturate 1.35 | 已有玻璃；高光、厚度、按钮尺度与原生仍有差异 |
| 模态遮罩 | 原有 50% 黑色 | 批准示例仅约 10% 蓝灰遮罩，两者不是同一合成条件；既有要求禁止弱化原遮罩，不能直接照搬示例数值 |
| 模态外壳 | 白色约 44%→22%，blur 18、saturate 1.45、brightness 2 | 最明显缺陷是背景亮度差被放大；应在保留遮罩的条件下统一承载与亮度，而不是继续叠加模糊 |
| 弹窗内部 | 实体输入框、透明区、不同白板交替 | 需要有意划分输入/正文/控制层。目前不少差别来自旧模板，呈现“拼接”感 |
| 菜单/Popover | 与模态部分共用材质变量 | 菜单、模态不能只凭共用一条滤镜认定等效；此次未逐个菜单完成动态背景检验 |
| 终端/日志/图表 | 必须维持稳定内容表面 | 不应为了“像玻璃”把正文、终端或数据色一并透明化 |

原生认证弹窗本身也有较实的灰色表面、白输入框和蓝主按钮。因此“某处不透明”不是充分的错误依据；错误是层级不清、同角色不一致、背景干扰和突兀断层。公共 API 不提供系统设置各层的固定透明百分比，本报告不编造这些数值。

## 三、字体与尺寸

字体栈已经包含系统字体，不能说当前完全没用系统字体。失败在字号、字重、行高和对齐的系统性。

| 角色 | 已知当前值/表现 | 审查判断 |
|---|---|---|
| 正文 | 14px、全局 line-height 1.5；安全正文又为 0.9rem（默认根字号下 14.4px） | 14px 本身合理；需消除同角色漂移 |
| 普通按钮 | 14px、400、至少 34px 高 | 不能全站一种外形；按普通、紧凑、主操作、危险操作统一 |
| 安全按钮 | 0.8rem（默认 12.8px）；表格动作固定 2rem 高、6rem 宽 | 密度被固定宽度破坏，不是把字再缩小就能解决 |
| 分组标题 | 多处 15px/16px、rem 或 em 值 | 应固定语义层级，同类标题同大小/字重/上下间距 |
| 弹窗标题 | 裸 h2 与专用 header 不同，部分约 21px，另一些更小 | 目前同级窗口视觉重量不一致 |
| 次要/技术文字 | 多种 0.8/0.85/0.875rem 与内联 px | 保持原要求至少 12px，不机械复制原型 10/11px |
| 数值 | 字重、大小、单位安排不统一 | 主要数值适当轻字重、等宽数字，单位明确，不能删精度换取简洁 |

本机 AppKit 返回系统字体 `.AppleSystemUIFont`；默认 systemFontSize 13pt、small 11pt、mini control 9pt、labelFontSize 10pt。这些是 API 默认值，不是“系统设置所有字都是 13pt”，也不能把 Retina 图上的 26 个像素当作 26px 文字。最终网页尺寸应以阅读性和原需求的层级为准，不套一张所谓 Apple 通用字号表。

## 四、本机实际语义色与当前差异

下表是在本机分别以 Aqua / DarkAqua 解析到 sRGB 的公共 AppKit 色值。没有切换用户外观。强调色受用户偏好影响；实际玻璃上的像素还会受背景合成影响。Apple 建议用随外观适配的语义色，而非假设固定 RGB 在所有外观下通用。[Apple Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)

| 语义 | 浅色 | 深色 | 用途/当前差异 |
|---|---|---|---|
| 当前强调色 | #007AFF | #007AFF | 主操作/焦点等；当前混用 #087cf0、#0664c4、#3b82f6、#2563eb |
| 系统蓝 | #0088FF | #0091FF | 与强调色并非同一 token，不能所有蓝强行相同 |
| 红 | #FF383C | #FF4245 | 当前 #f43f5e/#e11d48 偏玫红；危险语义必须保留 |
| 绿 | #34C759 | #30D158 | 当前 #10b981/#059669 偏青绿 |
| 橙 | #FF8D28 | #FF9230 | 当前 #f59e0b/#d97706 更偏琥珀；告警不能只靠颜色 |
| 黄 | #FFCC00 | #FFD600 | 不适合作为白底小字颜色；适合受控面积的提示图形 |
| 粉 | #FF2D55 | #FF375F | 系统确实使用粉色，不存在“Mac 不用粉色”规则 |
| 紫 | #CB30E0 | #DB34F2 | 当前 violet #8b5cf6 偏另一套色阶 |
| 靛蓝 | #6155F5 | #6D7CFF | 与紫/蓝有独立语义，不应随意增加装饰色 |
| 青绿 | #00C3D0 | #00D2E0 | 系统有该颜色，但成功状态不应因旧色阶偶然变成青绿 |
| 青蓝 | #00C0E8 | #3CD3FE | 当前 cyan #06b6d4 不一致 |
| 棕 | #AC7F5E | #B78A66 | 并非禁用色；主文字不应染成装饰棕/卡其 |
| 灰 | #8E8E93 | #98989D | 不是所有辅助文字的唯一灰色 |
| 选中内容背景 | #0064E1 | #0059D1 | 再次说明不同角色可以有不同蓝色 |

文字/分隔的 API 结果：浅色主 label 是黑色约 84.7% alpha、次级 49.8%、三级 25.9%、禁用 24.7%、分隔 9.8%；深色对应白色 84.7%、54.9%、24.7%、24.7%、9.8%。窗口/控制背景 API 为浅色 #FFFFFF、深色 #1E1E1E。**这些不是原生截图所有区域的直接最终颜色**，不能拿三级 label 的 alpha 不分背景直接用于必须清晰的表单文字。

色彩使用原则：中性白/灰承载信息，蓝色表达操作与选中，红/绿/橙主要承担状态；保持文字和图标辅助识别，减少整行/整卡染色。macOS 没有“绝不使用某种色相”的清单，当前问题是角色混乱、颜色面积过大、饱和色互相竞争。

也不能全局搜索替换上述 hex：例如本机系统绿对白对比度约 2.22:1，系统蓝约 3.52:1，直接拿来作白底小字会低于原需求 4.5:1。应区分彩色填充/图标和可读文字色，并在真实合成背景校核。LED 用户色、ANSI、图表数据色不属于皮肤统一范围。

## 五、批准示例与现实现，以及示例自身的缺口

| 项目 | 示例中已有、当前没落实 | 示例自身也不能直接当原生标准的部分 |
|---|---|---|
| 设置行 | 标签与值/控件同排、分隔与行距较整齐；当前多处仍是旧后台表单堆叠 | 仅少量短文本/简单数据，没有全部真实分支与长名称 |
| 按钮 | 弹窗主操作明确蓝底；当前多个主操作仍白底 | 紧凑控件部分 11px，不能照搬到生产可读性要求 |
| 材质 | 示例没有 brightness(2)，观感更连续 | 遮罩明显更轻，与生产必须保留原遮罩的约束不同 |
| 字体 | 示例 root 14px，标题和数值重量较有秩序 | 仍是 CSS 模拟，不是完整原生字体/控件度量；不能全盘复制 |
| 卡片 | 小框、徽章、彩色状态面积更克制 | 示例简化/整合了内容；生产三个独立模块不能合并来换取同样外形 |
| 深层页面 | 系统、文件、少量弹窗可比较 | 安全等大量导航只是占位，没有批准过完整安全页或复杂自动化编辑器 |
| 原生感 | 能作为已批准视觉方向 | 静态壁纸、固定 CSS 材质和简化状态仍不等同原生 Liquid Glass |

此次以真实系统感觉为主要审查基准，同时保留批准的暖金/浅蓝背景、产品原有导航及功能边界。无需重新选风格；也不能用“原型没画安全页”解释为什么安全页可以沿用旧样式。

## 七、是否真实机器运行就会改善

**不会自动改善。** 页面由当前客户端 Safari/Chromium 渲染，TianshanOS 设备提供资源和数据。相同浏览器、前端文件、视口与数据下，切换静态资源服务器不会重新排版按钮或自动套用原生控件体系。此次已经在用户实际 Mac 的 Safari 看到了上述问题。

确实可能造成差异的因素是浏览器引擎、缩放、视口宽度、字体回退、缓存文件版本、系统透明度设置和实际数据长度。原生 select 的外观尤其可能跨浏览器不同。真实设备更长的主机名/证书信息还可能增加拥挤，而不是改善它。受控数据验证不能替代设备数据验收。

此前修复的 CSS 压缩问题应单独看待；当前问题在最终构建和 Safari 中仍然存在，不能继续全部归因于压缩器、模拟窗口或截图工具。
