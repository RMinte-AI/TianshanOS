# TianshanOS 密钥生成和存储修复方案

日期：2026 年 10 月 9 日。状态：本地实施和验证完成，详见 [RESULT.md](RESULT.md)；原间歇性故障仍待捕获，尚未刷机。

本次修复围绕安全页的“生成新密钥”：保存结果必须真实，生成过程必须有持续反馈，收到结果后必须正确更新界面。修复已经复现的元数据、索引处理缺陷，并补齐这一操作的诊断记录。此前间歇性反馈异常尚未捕获失败请求，本方案不将它预先归因于 HTTP 超时、连接清理或界面错误。

## 成功和失败的定义

新生成密钥只有在私钥、公钥、元数据、索引写入及现有提交调用均成功后，才确认保存完成。元数据继续保存当前的类型、备注、别名、时间、`exportable`、`hidden` 和公钥存在标志，不改变字段名或含义。

新生成密钥的公钥导出、缓冲区分配或写入失败，应使生成操作失败，不能继续返回一个缺少公钥的“生成成功”结果。通用私钥导入仍允许不提供公钥，保留其可选公钥合同；不能把这一生成要求扩展到所有导入操作。

保存完成、HTTP 发送完成、浏览器收到响应和列表刷新完成是不同事实。保存完成后，响应构造或发送失败不得触发密钥删除，也不得自动再次生成。

## 新建写入流程

1. 在生成 RSA 或 ECDSA 前验证新 ID 和索引可读性。新 ID 必须非空，不能包含索引分隔符逗号；构造出的 NVS 名称必须满足 SDK 的长度限制。当前后缀 `_priv`、`_meta` 占 5 字节，因此这个格式下的新 ID 最长为 10 个 UTF-8 字节。保持原 ID 缓冲区大小和旧记录读取方式，不做改名或迁移。
2. 在写锁内检查该 ID 的索引项及 `_priv`、`_pub`、`_meta` 是否已存在。任何已有组成部分都表示 ID 已占用，新建不得覆盖。NVS 读取出错必须返回错误，不能当成“不存在”。这一规则与现有 CLI 生成和导入的拒绝同 ID 行为一致。
3. 检查新增索引是否超过现有 8 项或缓冲区容量。超过时在生成前拒绝，不能截断索引。NVS 剩余条目只用于诊断，不用估算阈值承诺一定能保存。
4. 释放写锁，执行现有密钥生成和导出，避免把耗时 RSA 运算放在存储锁内。复用现有私钥清零和释放逻辑。
5. 再次取得写锁，重新检查 ID 占用和索引容量。前一次检查不能代替这里的检查，因为生成期间其他入口可能写入。
6. 按私钥、公钥、元数据、索引的顺序写入，索引最后发布。必需步骤失败立即停止后续正常写入，转入新建失败清理。
7. 现有提交调用成功后确认保存完成，释放锁和临时资源。诊断结果通过调用者提供的结果对象返回，不使用共享的“最后一次错误”变量。

索引比较必须按逗号分隔的完整 ID 进行，`p` 与 `app`、`key1` 与 `key10` 都不同。使用局部解析状态，检查完整输出长度，禁止通过 `strncat` 截断后仍返回成功。

一个局部写锁保护存储写入、索引修改、新建失败清理，以及同模块中会交叉修改这些记录的删除和 `last_used` 更新。内部不加锁的辅助函数由入口持锁调用，不能在持锁路径再调用会取得同一锁的公开函数。锁的初始化和关闭处理限于这个模块，不增加后台任务或改写系统生命周期。

## 新建失败清理

当前 ESP-IDF 的 `nvs_commit()` 不提供多条记录的事务回滚。不能认为提交前的写入尚未落盘，也不能把“提前返回错误”等同于“没有残留”。

清理必须满足以下规则：

- 写入前确认目标各组成部分不存在，记录本次已经执行或可能部分执行的写入；不触碰其他 ID。
- 未尝试发布索引时，不修改原索引。尝试发布索引后发生失败时，在同一写锁内读取和核对索引；需要撤销时，只恢复本次改变的索引状态。
- 索引恢复失败时停止删除密钥材料，报告恢复未完成，避免进一步制造索引指向缺失数据的状态。
- 索引已恢复或未改变时，清理本次新 ID 的元数据、公钥和私钥。不存在的本次条目可视为已清理；其他错误不得吞掉。
- 分别保留原始失败错误和清理错误。清理失败不能改报成功，也不能用清理错误掩盖最初失败阶段。
- 不调用目前忽略删除错误的 `ts_keystore_delete_key()` 作为失败回收。使用限定本次新 ID、检查每一步结果的内部辅助函数。

公共存储函数的元数据、索引错误也必须传播给现有导入调用方，不能继续虚报成功。正常导入保持现有合同。通用存储入口对已有 ID 的写入，不执行新建删除回滚；本方案不增加已有密钥的原子替换能力。若实现必须改变已有 ID 替换语义，须单独提交范围说明，不能夹带实施。

本次验收覆盖正常运行中的写入和清理失败，不承诺多记录写入期间任意断电都能自动恢复。断电事务或历史数据修复需要另一个明确方案。

## 接口和错误合同

现有 `ts_keystore_generate_key_ex` 及其他公开 C 函数的签名保持不变。增加一个生成专用的带结果入口，由旧函数包装调用；两者使用同一实现。结果对象只提供失败阶段、清理错误和是否已确认保存完成，供 `key.generate` 使用。CLI 不需要改调用方式。

REST 成功结构保持现有合同：

```json
{"code":0,"data":{"generated":true,"id":"testtest","type":"rsa2048"}}
```

失败继续使用非零业务码，补充生成专用诊断数据，例如：

```json
{
  "code":7,
  "error":"key_storage_failed",
  "data":{
    "id":"newkey",
    "failed_stage":"metadata_write",
    "esp_error":"ESP_ERR_NVS_NOT_ENOUGH_SPACE",
    "cleanup_complete":true,
    "cleanup_error":"ESP_OK"
  }
}
```

示例中的数值沿用当前 `TS_API_ERR_INTERNAL`，不增加通用 API 错误枚举。`cleanup_complete` 只描述本次新建数据的清理结果。失败响应不通过 `generated=false` 暗示设备没有任何残留数据。

| 情况 | 页面必须得到的含义 |
|---|---|
| ID 不合法 | 未开始生成，指出输入问题 |
| ID 已占用 | 未覆盖已有密钥 |
| 达到索引数量上限 | 当前不能新增，不改容量配置 |
| `ESP_ERR_NO_MEM` | 内存分配不足 |
| `ESP_ERR_NVS_NOT_ENOUGH_SPACE` | NVS 存储空间不足，不能误标为内存不足 |
| 必需写入失败且清理完成 | 生成保存未完成，本次新建数据已回收 |
| 清理失败 | 原错误和清理错误均可见，存储状态需要处理 |
| 保存完成但响应构造或发送异常 | 已完成保存的密钥保持不动，客户端结果可能未知 |

`ts_webui_api.c` 只为 `key.generate` 保留错误响应中的这些 `data` 字段，其他端点的序列化合同不变。生成成功结果对象的构造失败必须记录为响应阶段错误；不得反向运行存储失败清理。

维持现有支持的类型和别名。界面 `ec256`、`ec384` 分别对应响应中的 `ecdsa-p256`、`ecdsa-p384`，不能用原始字符串相等判断它们是否生成成功。默认 RSA 类型及现有 ECDSA 的 SSH 使用提示保持原样。

## 页面状态和归属

在弹窗中增加持续的状态区域。现有短时 toast 可以保留，但不能作为生成期间唯一反馈。

| 状态 | 显示和动作 |
|---|---|
| 可提交 | 使用现有字段和默认值 |
| 正在生成 | 显示本次 ID 和持续进度，禁用重复生成 |
| 保存成功 | 验证 `code=0`、`generated=true` 和返回 ID；关闭所属弹窗，提示成功，刷新密钥表 |
| 保存失败 | 显示具体原因及清理结果，保留输入，不显示成功 |
| 结果未知 | 网络失败、超时、错误格式、不完整成功结构或无法判断操作结果的 HTTP 错误；不自动重发生成请求 |
| 核对当前记录 | 对结果未知执行最多一轮现有只读查询及列表刷新 |

`key.info` 查到同 ID 只证明当前记录存在，不证明这一次请求生成成功，也不证明私钥和公钥材料完整。查询没有找到记录，可能是设备仍在生成，不能据此断言失败。补查失败时保持“结果未知”。

操作期间关闭弹窗仅关闭界面，不取消设备的 RSA 生成；按钮和说明应表达这一点。明确的失败允许用户修改输入后重新提交；用户手动再提交是一个新请求，后端仍需重新检查 ID 占用。全流程禁止自动重试生成。

前端记录一个当前生成操作和弹窗实例标识，复用现有页面有效性检查。旧请求返回时，不能关闭后来打开的其他弹窗、覆盖新输入或把错误写入已切换的页面。`finally` 只能解除本次拥有的按钮状态，不能解除另一操作的禁用状态。

`refreshSecurityPage` 只增加密钥列表的明确加载结果及密钥表更新的有效性判断，保持其他安全模块请求和行为。生成已被确认成功后，列表刷新失败只能提示“密钥已生成，但列表刷新失败”，不能改说生成失败。必要的刷新序号仅限制密钥表更新，不能重写整个页面的刷新架构。

## 生成专用诊断

为 `key.generate` 增加可选的短请求编号。新前端提供编号；旧客户端和 CLI 不提供时仍能正常使用。编号只关联日志，不参与权限、密钥身份、存储命名或持久化。

服务端只记录这个端点的请求到达、生成和保存返回、响应构造、发送返回值及耗时。失败时记录 ID、阶段、原始错误和清理错误。必须覆盖 JSON 构造失败分支，不能只在正常发送路径打日志。

前端只记录这个操作的提交、响应头到达、响应体读取和解析、业务判断、弹窗关闭及列表刷新。记录 HTTP 状态、正文长度、有限的业务结果和异常类型，不记录私钥、公钥正文、认证头、token 或完整请求体。

正式实现不使用调查期间的全局函数替换。服务端复用现有日志缓冲区；前端只保留最近一次生成的有限阶段记录，不使用持续增长的数组，不监听所有请求，不复制完整响应体，也不增加定时轮询。

| 捕获结果 | 可以成立的判断 |
|---|---|
| 设备未确认保存完成 | 继续检查生成和存储阶段，不能先归因于页面 |
| 已确认保存，响应构造失败 | 故障在构造响应阶段 |
| 已确认保存，发送返回错误 | 故障在服务端发送阶段，客户端是否已收到部分数据仍需结合浏览器记录 |
| 发送返回成功，浏览器未获得完整响应 | 发送成功只表示服务端调用成功，不能证明浏览器接收成功 |
| 浏览器获得完整成功响应，所属弹窗未关闭 | 检查业务解析、JavaScript 异常和界面归属 |
| 已执行关闭，动画结束后弹窗仍可见 | 检查 DOM 与样式，而不是密钥保存 |
| 弹窗关闭、成功提示出现，但列表不更新 | 检查列表读取、渲染和过期响应覆盖 |

不能只因缺少一条日志就断言该阶段没有执行，也不能把样式动画开始时瞬间的 `opacity=0` 判为提示失败。诊断必须结合日志保留情况、操作归属和稳定后的页面状态。

原间歇性故障只有在捕获失败请求、确定失败点并验证对应修复后，才能标为已解决。当前正常记录只能作为正常基线。

## 验收矩阵

### 存储与接口

下面的必需写入失败矩阵以“生成新密钥”为对象；私钥导入另外验证其可选公钥合同。

| 场景 | 必须满足 |
|---|---|
| 私钥、公钥、元数据、索引、提交分别失败 | 对应必需步骤不得返回成功；失败阶段和原始错误准确 |
| 清理成功 | 新 ID 的本次材料和索引不残留；其他 ID 的数据不变 |
| 清理、索引恢复或清理提交失败 | 明确报告恢复未完成；不继续破坏索引与材料的对应关系 |
| 已有 ID 或历史残留 ID | 新建不覆盖、不删除；已有内容逐字节保持 |
| `app` 与 `p`、`key1` 与 `key10` | 按完整 ID 独立处理 |
| 长度超限或逗号 ID | 在耗时生成前拒绝；NVS 写入数为零 |
| 达到 8 项、索引容量不足或索引读取失败 | 明确拒绝；不截断、不把读取失败当成空库 |
| 两个入口同时新建相同或不同 ID | 相同 ID 只有一个发布结果；不同 ID 不丢索引项 |
| 新建与删除、时间更新交叉 | 无锁递归和死锁，不回滚其他 ID 的变化 |
| 私钥导入、公钥可选、旧格式读取 | 正常合同保持；元数据和索引失败能传播 |
| API 响应分配或序列化失败 | 已保存记录不被删除，不伪造完整成功响应 |
| CLI 生成与导入 | 现有调用签名、成功路径和已占用 ID 的拒绝行为保持 |

主机测试执行实际生产函数，模拟外部 NVS 和加密接口。NVS 模型必须在 `set` 时立即改变数据，不能用假的多记录事务掩盖清理错误。使用 ASan 和 UBSan 检查释放、越界和资源平衡；测试不输出私钥内容。

### 页面与浏览器

覆盖中英界面和四个现有密钥类型：正常返回、3 秒以上的正常生成、超过前端期限、明确业务失败、HTTP 异常、响应体读取中断、非法 JSON、缺失成功字段、错误 ID、列表读取失败和补查失败。

正常路径应关闭所属弹窗、显示成功且列表出现新记录；失败和未知路径应有持续状态，保持输入且不自动再次 POST。连续点击只能产生一次进行中的生成请求。关闭重开、切换页面、乱序返回和语言切换不得更新错误归属的界面。

真实浏览器测试使用本机模拟 API。缓存升级测试必须启用真实 HTTP 缓存，不能使用会禁用缓存的路由拦截来冒充缓存验收。反向检查：恢复原来吞错或子串匹配的实现，对应测试必须失败。

### 构建与真机

本机相关测试通过后，运行现有运行时和前端回归，并在独立目录从同一份当前源码构建固件和 Web 镜像。存储修复需要新固件，页面和缓存修复需要新 Web 镜像，不能只更新其中一个就宣称整体完成。确认 SSH 部署、HTTPS 行和当前 LPMU 正常路径没有因公共文件修改而变化。

真机验证只在明确的设备操作授权范围内执行。使用用户同意的新 ID，核对设备记录、HTTP 返回、弹窗、提示和列表；已有密钥及部署主机保持。空间不足和清理失败主要通过故障注入验证，不用填满或清空生产 NVS 来制造故障。

主机模拟不证明实际 flash 页回收或断电恢复；构建成功不等于真机验收。修复后的真机结果必须单独记录，不能复用 `testtest` 的修复前正常记录。

## 实施顺序与停止条件

1. 冻结实施起点的相关文件差异，先把三个旧缺陷转成可失败的回归测试。
2. 修正必需写入、完整 ID 索引、新建保护和失败清理；验证导入及旧记录兼容。
3. 补充生成专用结果和 API 错误传递，检查错误 DTO 和响应阶段不触发存储回滚。
4. 实现页面状态、归属、一次只读补查和列表结果区分，再补充生成专用诊断。
5. 更新受影响资源的缓存标识，运行相关回归、独立构建和授权的真机验收。

每一步仅修改范围表内的职责。出现需要修改分区、存储格式、旧密钥替换合同、全局 HTTP 参数或其他功能才能完成的情况，先明确新证据、必要性和影响，单独讨论，不能自行扩面。

交付时分别标明：三个已复现存储缺陷的验证结果、页面反馈合同的验证结果、原间歇性故障是否已捕获并定位。原故障仍未复现时必须保留这一状态，不能以新增日志或一次正常生成替代根因结论。
