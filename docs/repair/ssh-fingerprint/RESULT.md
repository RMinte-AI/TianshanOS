# SSH 主机指纹确认框弹不出：修复结果

## 现象

SSH 主机页点「测试连接」：目标主机是新的（还没登记指纹），或它的指纹和已登记的不一样时，页面只显示「连接失败」，没有确认框，用户在这个入口无法信任新主机、也无法核对并接受指纹变化。

## 根因（三处接力丢失）

1. 固件：`ssh.exec` 遇到新主机返回业务码 `1002`、指纹变化返回 `1001`，并把指纹放进 `result->data`；同时返回值是 `ESP_ERR_INVALID_STATE`（`ts_api_ssh.c` 的 `verify_host_fingerprint`）。
2. HTTP 出口：返回值非 `ESP_OK` 且业务码非 0 时走 `ts_webui_api.c` 的通用失败分支，该分支只输出 `{code, error}`，把 `data` 释放了。
3. 页面：`testSshHostByIndex` 必须取到 `data.fingerprint` / `data.current_fingerprint` 才弹确认框；取不到就跳过，显示连接失败。

`ssh.test` 对同样的状态返回 `ESP_OK`，走成功分支，`data` 保留，所以直接调用 `ssh.test` 不受影响；页面用的是 `ssh.exec`。

原有测试没发现，是因为它们直接替换 `api.call`，或者让模拟设备在失败响应里带 `data`，绕过了真实的 HTTP 序列化。

## 修复

`ts_webui_api.c` 的通用失败分支同样输出处理函数留下的 `result.data`。没有 `data` 的失败响应字节不变（仍是 `{"code":N,"error":"..."}`）。

固件的指纹校验逻辑没有改：新主机必须带回当前连接上看到的那个指纹（`confirmed_fingerprint`）并显式 `trust_new`，指纹变化必须带回当前指纹并显式 `accept_changed`，否则继续拒绝；校验失败时不会发送凭据、不会执行命令。

## 验证（均未接触真机）

- `tests/runtime/test_ssh_fingerprint_wire.py`：把生产代码里的 `ssh.exec` / `ssh.test` 处理函数和 `ts_webui_api.c` 的响应分支原文抽出来，配合合成的 SSH / known-hosts 后端运行，检查线上字节：新主机、指纹变化的响应带指纹；没有精确确认时不信任、不发凭据、不执行命令；错误或缺失的确认仍被拒绝；普通失败仍是 `{code,error}`；`API not found` 仍是 404。线上字节存为契约夹具 `tests/fixtures/ssh-fingerprint/`，与代码不一致时测试失败。
- `tests/prompts/ssh-fingerprint.browser.test.cjs`：把这些夹具原样回放给真实页面（真实 `api.js`、真实「测试」按钮、真实确认框），中英文各自检查：确认框显示设备发来的指纹；取消后不信任、不重试；确认后恰好发送用户看到的那个指纹，且 `trust_new` / `accept_changed` 与状态码对应；确认时设备换了另一把密钥则不信任、不循环。
- 反向验证：还原修复后运行时测试断言失败；夹具换成旧固件的线上格式后浏览器测试失败。
- `test_keystore.py` 中原有一条断言钉着「其他接口的失败响应不带 data」（0.6.1 为控制范围有意保留，模拟接口的字段就叫 `should_omit`），已按新决定改为断言带上——该文件只改了这一条断言和模拟字段的名字（共 2 行）。密钥生成原有的失败测试全部保留：失败阶段（`failed_stage`）、清理结果（`cleanup_complete`）、响应序列化失败返回 HTTP 500 并保留已生成的密钥，等等。逐一破坏对应的生产代码（失败细节不再送出、清理结果缺失、序列化失败不再返回 500），这些旧测试分别报错。
- 分配失败遍历：在构建失败响应的每一个可能分配失败的点注入失败，响应只能是完整的 `{code,error[,data]}`（`data` 要么完整要么没有）或 HTTP 500。遍历发现了一个原有的漏洞：写入 `code` 时分配失败，会发出缺 `code` 的残缺 JSON。已一并加固——失败分支里 `code` / `error` 写不进去就改发 500（正常情况输出不变）。成功分支有同类写法，这次没有改。
- 其他：运行时全套 41 项、静态 122 项、浏览器 249 项（原 232 + 新增 17）、发布检查通过；ESP-IDF 5.5.2 完整编译通过，镜像大小不变（2,202,336 字节）。
- 排查：全部接口处理函数里，失败时可能同时带着 `data` 的共 13 个，字段名中没有密码、私钥、令牌一类（按字段名的启发式检查）。

## 行为变化

其他接口的失败响应现在也可能带 `data`——只限处理函数主动留下的细节（服务状态、测试输出、指纹等）。已逐个核对页面里对这些接口的调用点（`automation.rules.get`、`actions.get` / `execute`、`sources.add`、`proxy.*`、`services.*` 等）：都是先判断 `code` 再使用 `data`，不依赖失败响应没有 `data`；`variables.set`、`test.ssh` 页面并不调用。

## 尚未验证

真机。建议刷机后检查：(1) 对一台从未连接过的主机点「测试连接」→ 出现确认框；取消 → 不登记；再点并确认 → 连接成功且已登记。(2) 把已登记主机换一把 SSH 主机密钥后点「测试连接」→ 出现确认框并显示新指纹。

## 附：指纹变化时的确认框（单独提交，可选）

修好之后「指纹变化」也会弹确认框，但原来的框和「新主机」完全一样：不说指纹变了，也不显示已登记的旧指纹。指纹变化可能是服务器重装，也可能是中间人攻击，用户很容易当成普通确认点过去。

单独的一个提交把它改成安全警告：标题「安全警告：主机指纹不匹配」，说明可能的原因，同时显示已登记的指纹和当前指纹，确认按钮写「更新主机密钥」，默认焦点落在「取消」（按回车等于取消）。文案全部沿用已有的 `securityPage.*` 语言包条目（原先那个再也打不开的旧弹窗用过），没有新增翻译；新主机的确认框不变。`index.html` 里 `app.js` 的缓存版本串同步提升为 `0.6.1-lpmu6-keygen2-fp1`。

如果不想要这部分，丢掉该提交即可，前一个提交（修复本身）可独立使用。
